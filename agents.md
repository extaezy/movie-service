# AGENTS.md

## Назначение проекта

Movie Service — веб-сервис поиска и оценки фильмов. Пользователь может найти фильм в каталоге TMDB, открыть подробности, поставить оценку, написать рецензию, сохранить фильм в список и взаимодействовать с другими пользователями. Сервис также агрегирует профессиональные рецензии критиков.

## Состояние проекта

Репозиторий содержит согласованную спецификацию MVP. Основные рабочие каталоги должны быть организованы так:

```text
backend/       FastAPI, SQLAlchemy, Alembic, pytest
frontend/      React, TypeScript, Vite
docs/          требования, архитектура, БД, API и frontend-план
```

Текущий MVP не включает сериалы, мобильное приложение, чат, realtime-уведомления, OAuth, восстановление пароля, сложные рекомендации, машинный перевод, автоматический анализ тональности, лайки/комментарии и произвольный scraping.

## Архитектура

- Frontend: React + TypeScript + Vite, маршрутизация через React Router, HTTP через Axios.
- Backend: Python 3.13, FastAPI, SQLAlchemy 2, Alembic, Pydantic, HTTPX, APScheduler.
- Хранилище: PostgreSQL; для локальной разработки допускается Docker Compose.
- Внешние источники: TMDB и один автоматический англоязычный источник критических рецензий; русскоязычные материалы добавляются вручную.
- Frontend обращается только к backend. Ключи внешних сервисов никогда не передаются в браузер и хранятся в `.env`.

Основные backend-модули: `auth`, `users`, `movies`, `lists`, `ratings`, `reviews`, `friendships`, `critic_reviews`, `admin`.

## Функциональные правила

- Списки фильмов: `watchlist`, `watched`, `favorite`.
- Оценка пользователя — целое число от 1 до 10; на пару пользователь/фильм приходится одна оценка.
- Пользователь может создавать, изменять и удалять только собственные рецензии.
- Профиль бывает открытым или закрытым. Владелец видит всё; друг видит закрытые списки и рецензии; посторонний видит только базовые данные закрытого профиля.
- Оценка закрытого профиля участвует в агрегате анонимно, текст рецензии скрывается.
- Дружба хранится единожды для пары пользователей с нормализованными ID и статусами `pending`, `accepted`, `rejected`.
- Фильмы синхронизируются из TMDB администратором; профессиональные рецензии должны хранить источник, критика, язык, ссылку, выдержку, оценку и вердикт.

## Контракты и документация

Перед изменением API, модели данных или пользовательских сценариев изучи соответствующий файл:

- `docs/requirements.md` — границы MVP и сценарии;
- `docs/architecture.md` — компоненты и технический стек;
- `docs/database.md` — сущности, связи и ограничения;
- `docs/api.md` — REST-контракт и коды ошибок;
- `docs/frontend.md` — маршруты, компоненты, состояния и wireframes.

Новые endpoint'ы, поля и ограничения сначала отражай в документации, если они меняют согласованную спецификацию.

## Frontend-ожидания

Обязательные маршруты: каталог `/`, фильм `/movies/:id`, вход `/login`, регистрация `/register`, профиль `/profile/:username`, редактирование `/profile/me/edit`, списки `/lists/:type`, друзья `/friends`, администрирование `/admin`.

Каждая страница должна иметь состояния `loading`, `success`, `empty`, `error`. Во время мутаций кнопка блокируется, а ошибка запроса отображается пользователю. Типы TypeScript должны соответствовать `docs/api.md`.

## Backend-ожидания

- Валидируй входные данные через Pydantic.
- Проверяй авторизацию и права доступа на backend, а не только в интерфейсе.
- Не раскрывай существование приватных данных через ошибки и ответы API.
- Для внешних API используй таймауты, нормализацию ответов и понятные ошибки `502`.
- Изменения схемы БД оформляй миграциями Alembic.
- Секреты и локальные настройки добавляй только в `.env`; в репозиторий помещай `.env.example` без секретных значений.

## Git-процесс

- `main` должна оставаться запускаемой.
- Одна задача — одна ветка; для новых веток используй префикс `codex/`, если не задано иное.
- Изменения объединяются через Pull Request; перед merge код проверяет второй участник.
- Не коммить секреты, локальные базы, сборочные артефакты и содержимое `.env`.
- Сообщения коммитов используют префиксы: `feat:`, `fix:`, `test:`, `docs:`, `chore:`, `refactor:`.

## Правила работы агента

1. Перед изменением проверь существующую структуру и `git status`; не затирай чужие незакоммиченные правки.
2. Сохраняй границы MVP и сначала переиспользуй существующие контракты.
3. Делай небольшие атомарные изменения, соответствующие одной задаче.
4. После изменений запускай доступные проверки backend/frontend и обновляй документацию при изменении поведения.
5. В итоговом сообщении укажи, что изменено, какие проверки выполнены и какие ограничения остались.

## Критерии готовности

Задача считается готовой, когда реализация соответствует требованиям и API-документации, права доступа проверяются на backend, миграции применимы, frontend обрабатывает все обязательные состояния, тесты/линтеры проходят, а секреты не попали в git.
