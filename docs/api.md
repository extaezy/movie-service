# API-контракт v1

Базовый префикс: `/api`. Формат обмена: JSON. Защищённые методы требуют авторизацию.

`/api` — часть пути запроса, а не сетевой адрес. Адрес backend задаётся настройкой клиентской части; адрес базы данных и ключи внешних служб в браузер не передаются.

## Авторизация

```http
POST /auth/register
POST /auth/login
POST /auth/logout
POST /auth/refresh
GET  /auth/me
```

### Текущий этап: PostgreSQL и access JWT

В текущем приложении auth-маршруты доступны без префикса `/api`.

- `POST /auth/register` сохраняет прежний контракт: `username`, `email`, `password`, `password_confirm`; ответ `201` содержит только `username` и `email`. Дубли возвращают `409`, ошибки валидации — `422`.
- Ответ `422` при регистрации содержит массив `detail` с полями `loc`, `msg` и `type` для каждой ошибки. При отсутствии имени пользователя `loc` равно `["body", "username"]`, а `type` — `missing`. Значения из запроса, включая пароль и его подтверждение, в ответ не включаются.
- `POST /auth/login` принимает JSON `{"identifier":"username или email","password":"пароль"}`. Ответ `200`: `{"access_token":"<jwt>","token_type":"bearer"}`. Неверные учётные данные возвращают `401` с одинаковым сообщением; ошибки структуры запроса — `422`.
- Username сравнивается с учётом регистра. Email при входе нормализуется через `EmailStr`, как при регистрации; дополнительного приведения всего адреса к нижнему регистру нет. Пароль не нормализуется.
- `GET /auth/me` требует `Authorization: Bearer <jwt>` и возвращает `id`, `username`, `email`. Пароль и хеш не возвращаются.
- JWT подписывается HS256 и действует не более 30 минут. Обязательные claims: `sub` (внутренний UUID пользователя), `sid` (UUID сессии), `iat`, `exp`. Проверяются подпись, алгоритм, время, существование активного пользователя и действующая сессия. Недействительный или отсутствующий токен возвращает `401` с `WWW-Authenticate: Bearer`.
- `JWT_SECRET_KEY` задаётся в окружении или `backend/.env`; требуется случайный секрет длиной не менее 32 символов. Значения по умолчанию нет.
- Учётные записи хранятся в `movie_service.users` PostgreSQL. При регистрации пользователь и профиль создаются одной транзакцией; UUID создаётся один раз и сохраняется между перезапусками. UNIQUE-ограничения базы защищают email и username от конкурентных дублей; конфликт возвращает `409`. Приложение не использует `auth.users` Supabase.
- Неактивный пользователь (`is_active=false`) не может войти и не проходит `/auth/me`. При недоступности PostgreSQL зависимые запросы возвращают `503`.
- Вход создаёт отдельную сессию в PostgreSQL на фиксированные 7 дней. Access JWT действует до 30 минут, но не дольше сессии, и содержит обязательные `sub`, `sid`, `iat`, `exp`. Старые JWT без `sid` больше не принимаются: после обновления потребуется войти заново. Каждый защищённый запрос проверяет активность пользователя и связанной сессии в БД; роль продолжает читаться из БД.
- `POST /auth/login`, `POST /auth/refresh` и `POST /auth/logout` требуют заголовок `X-Auth-Request: 1`. Переданный браузером Origin должен входить в `AUTH_ALLOWED_ORIGINS` (JSON-массив адресов в настройках). Это защита cookie-операций от CSRF вместе с `SameSite=Lax`; для CLI без Origin также обязателен специальный заголовок.
- Login сохраняет непрозрачный случайный refresh token в host-only cookie `movie_service_refresh` с `HttpOnly`, `SameSite=Lax`, `Path=/`. В production используется HTTPS и `AUTH_COOKIE_SECURE=true`; для локального HTTP задаётся `false`. Refresh не возвращается в JSON. В БД хранятся только SHA-256 хеши refresh token и история их использования.
- `POST /auth/refresh` не требует действующего access: использует cookie, атомарно помечает refresh использованным и выдаёт новый access и новую cookie. JSON имеет тот же формат, что login. Конечный срок refresh и сессии остаётся от первого входа. Повторное использование старого refresh отзывает всю его сессию. Неизвестный, просроченный, отозванный refresh или неактивный пользователь — `401` с очисткой cookie; ошибка Origin/специального заголовка — `403`, отказ БД — `503` без очистки.
- `POST /auth/logout` идемпотентен: `204`, закрывает сессию из refresh cookie и/или действующего Bearer JWT, очищает cookie. Выход из одной сессии не закрывает другие устройства. Закрытый access перестаёт приниматься последующими запросами, даже до своего exp. Уже начавшиеся операции не отменяются. Все ответы login/refresh/logout используют `Cache-Control: no-store`. Продление после ошибки выполняется клиентом максимум один раз, при `403` или `503` обновление не запускается.

## Фильмы

```http
GET  /movies?page=1&genre_id=3&year=1999&sort=release_date_desc
GET  /movies/discover?page=1&tmdb_genre_id=28&year=1999&sort=popularity_desc
GET  /movies/search?q=...
GET  /movies/tmdb/{tmdb_id}
GET  /movies/{movie_id}
POST /admin/movies/sync
```

### Локальный каталог

`GET /movies` доступен без `/api` и JWT. Возвращает только фильмы, сохранённые в PostgreSQL.

- `page` — номер страницы от 1 до 2147483647, по умолчанию 1. Размер страницы фиксирован: до 20 фильмов.
- `genre_id` — необязательный внутренний ID жанра (`genres[].id` в карточке), от 1 до 2147483647. `year` — необязательный год выхода от 1 до 9999. При указании обоих фильтров фильм должен подходить под оба.
- `sort` — `release_date_desc` (по умолчанию), `release_date_asc`, `rating_desc` или `rating_asc`. Сортировка `rating_*` использует сохранённое поле `tmdb_vote_average` — оценку TMDB, а не среднюю оценку пользователей Movie Service. Отсутствующие значения выбранного поля идут в конце при обоих направлениях; при равных значениях порядок определяется по возрастанию внутреннего `id`. Сортировка применяется до пагинации и совместима с фильтрами жанра и года. Рейтинг TMDB хранится со времени импорта карточки и не обновляется этим запросом.
- Ответ `200` содержит `page`, `page_size` (всегда 20), `total_results` (количество фильмов после фильтрации), `total_pages` и `results` (массив карточек в формате ниже). Если подходящих фильмов нет, `total_results` и `total_pages` равны 0. Страница за пределами выдачи возвращает пустой `results` с фактическими общими счётчиками.
- Ошибки: `422` при неверных параметрах, `503` при недоступности базы данных.

### Витрина TMDB

`GET /movies/discover` доступен без `/api` и JWT. Backend запрашивает `/discover/movie` в TMDB. PostgreSQL для витрины не используется.

- `page` — от 1 до 500, по умолчанию 1. Размер страницы задаёт TMDB.
- `tmdb_genre_id` — необязательный внешний ID жанра (из `genre_ids` в выдаче TMDB), от 1 до 2147483647. `year` — необязательный год основного релиза от 1 до 9999. Оба фильтра можно применять вместе.
- `sort` — `popularity_desc` (по умолчанию), `release_date_asc`, `release_date_desc`, `rating_asc` или `rating_desc`. Для `rating_asc` backend передаёт в TMDB `sort_by=vote_average.asc`, для `rating_desc` — `vote_average.desc`. Сортировку и пагинацию выполняет TMDB; локальный рейтинг пользователей не используется. Дополнительный порог числа голосов не вводится.
- Ответ `200` имеет тот же формат, что и поиск. `total_pages` ограничен 500, `total_results` показывает общее число совпадений по данным TMDB. При отсутствии совпадений `results` пуст.
- Ошибки: `422` при неверных параметрах, `502` при сбое TMDB или некорректном ответе, `503` при отсутствии настройки TMDB.

### Поиск и открытие фильма

Реализованные маршруты доступны без `/api`, публично, без JWT:

- `GET /movies/search?q=Матрица&page=1` обращается к TMDB, не читает и не изменяет БД. `q` после удаления пробелов по краям содержит 1–200 символов; `page` — 1–500. Ответ 200: `page`, `total_pages`, `total_results`, `results`. Каждый результат содержит `tmdb_id`, `title`, `original_title`, `overview`, `release_date`, `poster_path`, `original_language`, `genre_ids`; необязательные текстовые поля и дата допускают null. `genre_ids` — внешние ID TMDB. Пустая выдача — 200 с пустым массивом.
- `GET /movies/tmdb/{tmdb_id}` открывает выбранный результат витрины или поиска: возвращает локальную карточку, если фильм уже есть; иначе получает подробности TMDB и сохраняет фильм, жанры и связи одной транзакцией. Успешный ответ имеет статус 200. Повторные и конкурентные открытия не создают дублей и не перезаписывают существующую карточку. Сохранение является внутренним наполнением кеша каталога, не правом редактирования фильма.
- `GET /movies/{movie_id}` читает карточку только по внутреннему ID из PostgreSQL, без обращения к TMDB. Неизвестный ID — 404.
- Карточка: `id` (внутренний), `tmdb_id`, `title`, `original_title`, `overview`, `release_date`, `poster_path`, `runtime`, `original_language`, `genres` (массив объектов `id`, `tmdb_id`, `name`). Неизвестная длительность, включая 0 от TMDB, возвращается как null. Путь постера не является полным URL. Все ID в пути — целые 1–2147483647.
- Для оценок, списков, рецензий и маршрута frontend `/movies/:id` используется внутренний `id` из карточки, а не `tmdb_id` поиска.
- Ответы `GET /movies/{movie_id}` и `GET /movies/tmdb/{tmdb_id}` дополнительно содержат `average_rating` (средняя оценка пользователей Movie Service по шкале от 1 до 10, округлённая до двух знаков) и `ratings_count` (количество оценок). Оценки закрытых профилей входят в агрегат анонимно. При отсутствии оценок `average_rating` равен `null`, а `ratings_count` равен `0`.
- В этих же ответах `tmdb_vote_average` (число от 0 до 10 с точностью до трёх знаков), `tmdb_vote_count` (число голосов) и `tmdb_rating_updated_at` (время сохранения в ISO 8601) показывают сохранённые данные TMDB. У ранее сохранённых фильмов и при отсутствии данных TMDB все три поля равны `null`. Если TMDB сообщает о нуле голосов, `tmdb_vote_count` равен `0`, `tmdb_vote_average` равен `null`, а время сохранения заполнено. Данные записываются при первом сохранении фильма.
- Ошибки: 422 — неверные параметры; 404 — фильм отсутствует или относится к adult-контенту; 502 — сбой TMDB или некорректные данные; 503 — отсутствует настройка TMDB либо недоступна БД. Сохранённая карточка доступна без токена и при сбое TMDB. Поиск по-прежнему требует доступного TMDB.

Административная синхронизация остаётся отдельным этапом. Автоматическое обновление сохранённых карточек и кеширование поисковой выдачи пока не реализованы.

### Похожие фильмы

`GET /movies/{movie_id}/similar` доступен без `/api` и JWT. `movie_id` — внутренний ID сохранённого фильма, целое 1–2147483647. Backend читает его `tmdb_id` из БД и запрашивает `/movie/{tmdb_id}/recommendations` в TMDB.

- Ответ `200`: объект с массивом `results` до 15 карточек. Формат карточек совпадает с элементами поиска: `tmdb_id`, `title`, `original_title`, `overview`, `release_date`, `poster_path`, `original_language`, `genre_ids`. Внутренний ID кандидата не возвращается; выбор карточки открывается через существующий `GET /movies/tmdb/{tmdb_id}`.
- Источник — до первых 150 результатов рекомендаций TMDB, полученных максимум с 8 страниц. «Топ» означает порядок выдачи TMDB, а не собственный коэффициент похожести. Backend случайно выбирает до 3 кандидатов из позиций 1–20 и до 12 из позиций 21–150, затем перемешивает результат целиком.
- Исходный фильм, `adult=true` и повторяющиеся `tmdb_id` исключаются до выбора. Позиции определяются по исходной выдаче, без сдвига после исключений. Если одна группа мала, свободные места заполняются случайными оставшимися кандидатами из другой группы до общего лимита 15. При нехватке кандидатов возвращается меньше 15; пустая выдача — `200` с пустым `results`.
- Каждый запрос заново получает пул и случайно выбирает результат. Подборка не кешируется и не записывается в БД, ответ содержит `Cache-Control: no-store`. Повторы отдельных фильмов между запросами допустимы: история подборок не хранится. Автоматического обновления блока по таймеру нет.
- Ошибки: `404` — исходный фильм не сохранён; `422` — неверный ID; `502` — сбой TMDB или некорректный ответ любой запрашиваемой страницы; `503` — отсутствие настройки TMDB либо недоступность БД. Частичная подборка при сбое страницы не возвращается. Чтение рекомендаций не меняет сохранённую карточку фильма.

## Пользователи и профили

```http
GET   /users/{username}
PATCH /users/me/profile
GET   /users/{username}/movies?list_type=watched
GET   /users/{username}/ratings
GET   /users/{username}/reviews
```

В закрытом профиле списки `watchlist`, `watched`, `favorite`, история оценок и полный список рецензий доступны владельцу и подтверждённым друзьям. Остальные посетители видят только `username` и аватар. Ответы профильных запросов не раскрывают содержимое, количество и наличие скрытых записей.

### Просмотр и изменение профиля

Маршруты доступны без префикса `/api`. Username в пути содержит 4–20 символов и сравнивается с учётом регистра.

- `GET /users/{username}` доступен гостю. Открытый профиль, а также закрытый профиль для владельца или подтверждённого друга возвращает `200` с полями `id` (UUID пользователя), `username`, `display_name`, `bio`, `avatar_url`, `is_private`. Необязательные поля профиля могут быть `null`. Email, роль и хеш пароля не возвращаются.
- Для остальных посетителей закрытого профиля ответ `200` содержит **только** `username` и `avatar_url`, без дополнительных полей и счётчиков. Заявки со статусами `pending` и `rejected` доступа не дают.
- `PATCH /users/me/profile` требует Bearer-токен и меняет только профиль владельца токена. Тело содержит хотя бы одно из полей: `display_name` (строка до 100 символов или `null`), `bio` (строка до 1000 символов или `null`), `avatar_url` (абсолютный HTTP/HTTPS URL до 2083 символов или `null`), `is_private` (строго boolean). `null` очищает необязательное поле; пропущенные поля сохраняются. Пустая строка допустима для имени и описания; нулевые символы в этих полях запрещены. URL сохраняется в нормализованной форме, backend не загружает изображение. `is_private: null`, пустой объект и лишние поля, включая `user_id`, `username`, `email`, `role`, отклоняются с `422`.
- Успешный `PATCH` возвращает `200` с полным профилем. Переключение `is_private` применяется к последующим запросам профиля, списков, оценок и рецензий пользователя.
- Ошибки: `401` при отсутствии токена для изменения или переданном недействительном Bearer-токене, `404` для отсутствующего профиля, `422` при неверных параметрах или теле, `503` при недоступности БД.
- Ответы профиля и профильных разделов имеют `Cache-Control: no-store`, включая `404` для отсутствующих или недоступных данных.

### Оценки и рецензии в профиле

- `GET /users/{username}/ratings?page=1` возвращает `page`, `page_size` (20), `total_results`, `total_pages` и `results`. Запись содержит `movie_id`, `score`, `created_at`, `updated_at`. Сортировка: от последних изменений по `updated_at`, при совпадении — по убыванию `movie_id`.
- `GET /users/{username}/reviews?page=1` возвращает тот же формат страницы с `page_size` 10. Записи имеют формат публичной рецензии фильма: `id`, `movie_id`, `text`, `contains_spoilers`, `created_at`, `author_username`. Сортировка: по убыванию `created_at`, затем `id`.
- Оба маршрута доступны гостю для открытого профиля; для закрытого профиля нужны владелец или подтверждённый друг. Отсутствующий пользователь и недоступный раздел возвращают одинаковый `404` с `detail: "Раздел профиля не найден"` независимо от наличия записей.
- `page` — целое число от 1 до 2147483647. Доступный пустой раздел возвращает `200`, пустой `results` и нулевые счётчики. Страница за пределами выдачи содержит пустой `results` и фактические счётчики. Недействительный Bearer-токен даёт `401`, неверные параметры — `422`, недоступность БД — `503`.

Эти ограничения не скрывают рецензии на страницах фильмов и не исключают оценки из среднего рейтинга фильма.

## Списки, оценки и рецензии

```http
POST   /movies/{movie_id}/lists          # {"list_type":"watchlist"}
DELETE /movies/{movie_id}/lists/{list_type}
PUT    /movies/{movie_id}/rating         # {"score":8}
DELETE /movies/{movie_id}/rating
GET    /movies/{movie_id}/reviews
POST   /movies/{movie_id}/reviews        # {"text":"...","contains_spoilers":false}
PATCH  /reviews/{review_id}
DELETE /reviews/{review_id}
```

### Личные списки фильмов

Маршруты списков доступны без префикса `/api`. `list_type` принимает `watchlist`, `watched` или `favorite`. Для записи и удаления требуются Bearer-токен и внутренний ID сохранённого фильма. Один фильм может находиться в нескольких списках.

- `POST /movies/{movie_id}/lists` принимает объект с обязательным полем `list_type`. Лишние поля отклоняются. Новая запись возвращает `201`, повторное добавление возвращает `200`. В обоих случаях тело содержит `movie_id` и `list_type`.
- `DELETE /movies/{movie_id}/lists/{list_type}` удаляет фильм из выбранного списка текущего пользователя. Возвращает `204` без тела, в том числе при повторном запросе для сохранённого фильма.
- `GET /users/{username}/movies?list_type=watched&page=1` возвращает `200` с полями `page`, `page_size` (всегда 20), `total_results`, `total_pages` и `results`. Параметр `list_type` обязателен. Параметр `page` принимает целые числа от 1 до 2147483647, по умолчанию 1.
- Для `list_type=watched` можно передать `q` и `genre_id`. `q` ищет часть названия без учёта регистра и содержит до 200 символов после удаления пробелов по краям. Пустое значение не ограничивает выдачу. `genre_id` — внутренний ID жанра из `genres[].id` в карточке фильма, от 1 до 2147483647.
- Поиск и фильтр применяются ко всему списку до подсчёта `total_results`, `total_pages` и выбора страницы. При передаче обоих параметров фильм должен соответствовать обоим условиям. Непустой `q` или `genre_id` для `watchlist` и `favorite` возвращает `422`.
- Каждая запись в `results` содержит `id`, `tmdb_id`, `title`, `poster_path`, `release_date` и `added_at`. Сначала идут недавно добавленные фильмы, при одинаковом времени — по убыванию `id`. Для доступного пустого списка оба общих счётчика равны 0. Для страниц за пределами выдачи `results` пуст, общие счётчики содержат фактические значения.
- Гость может читать списки открытого профиля. Списки закрытого профиля доступны владельцу и подтверждённым друзьям. Закрытый для запрашивающего список и отсутствующий пользователь возвращают одинаковый `404`.
- Ошибки записи и удаления — `401` при отсутствии действующего токена и `404` для отсутствующего фильма. Переданный недействительный Bearer-токен при просмотре даёт `401`. Неверные параметры или тело дают `422`, недоступность БД — `503`.

### Оценки фильмов

`PUT` и `DELETE /movies/{movie_id}/rating` доступны без префикса `/api` и требуют `Authorization: Bearer <jwt>`. `movie_id` — внутренний ID сохранённого фильма. Операции используют ID пользователя из токена.

- `PUT` принимает `{"score":8}`. `score` — строго целое число от 1 до 10. Запрос создаёт оценку или заменяет значение существующей оценки текущего пользователя. В обоих случаях ответ `200` содержит `movie_id` и `score`.
- `DELETE` удаляет оценку текущего пользователя. Ответ `204` без тела возвращается и при повторном удалении, если фильм существует.
- Ошибки: `401` при отсутствующем или недействительном токене, `404` если фильм не сохранён, `422` при неверном ID фильма или теле запроса `PUT`, `503` при недоступности БД.

### Просмотр пользовательских рецензий на фильм

`GET /movies/{movie_id}/reviews` возвращает опубликованные рецензии на сохранённый фильм по его внутреннему ID. Маршрут доступен без префикса `/api` и без токена. Рецензии авторов с закрытыми профилями входят в выдачу на общих основаниях. Правила доступа к спискам в профиле применяются к запросам `/users/{username}/...`.

- Параметр `page` задаёт номер страницы от 1 до 2147483647. По умолчанию возвращается первая страница. Размер страницы фиксирован и составляет до 10 рецензий.
- Ответ `200` содержит объект с полями `page`, `page_size` (всегда 10), `total_results` (общее количество рецензий фильма), `total_pages` и `results` (массив рецензий текущей страницы).
- Каждая запись в `results` включает `id`, `movie_id`, `text`, `contains_spoilers`, `created_at` и `author_username`. Рецензии отсортированы от новых к старым по `created_at`, при совпадении времени — по убыванию `id`.
- Для фильма без рецензий возвращается `200` с пустым `results` и нулевыми счётчиками `total_results` и `total_pages`. Страница за пределами выдачи возвращает пустой `results` с фактическими общими счётчиками.
- Ошибки — `404`, если фильм не сохранён, `422` при неверном ID фильма или номере страницы, `503` при недоступности БД.

### Создание пользовательской рецензии

`POST /movies/{movie_id}/reviews` доступен без префикса `/api` и требует `Authorization: Bearer <jwt>`. `movie_id` — внутренний ID сохранённого фильма. Автор определяется по токену. Выставлять оценку перед созданием рецензии не требуется.

- Тело запроса содержит `text` с текстом рецензии и необязательный булев `contains_spoilers` (по умолчанию `false`). Текст должен содержать хотя бы один непробельный символ и не может содержать нулевой символ. Лишние поля отклоняются.
- Ответ `201` содержит `id`, `movie_id`, `text`, `contains_spoilers` и `created_at`.
- Ошибки: `401` при отсутствующем или недействительном токене, `404` если фильм не сохранён, `409` если текущий пользователь уже написал рецензию на этот фильм, `422` при неверном ID или теле запроса, `503` при недоступности БД.

### Редактирование пользовательской рецензии

`PATCH /reviews/{review_id}` доступен без префикса `/api` и требует `Authorization: Bearer <jwt>`. `review_id` — положительный внутренний ID рецензии. Редактирование доступно только автору, включая владельца закрытого профиля.

- Тело содержит `text`, `contains_spoilers` или оба поля. Пропущенные поля сохраняют прежние значения. Пустой объект, `null` и лишние поля отклоняются. Правила текста и булева флага совпадают с созданием рецензии.
- Ответ `200` содержит `id`, `movie_id`, `text`, `contains_spoilers`, `created_at` и `updated_at`. Обновляется существующая запись с сохранением автора, фильма и времени создания.
- Ошибки: `401` при отсутствующем или недействительном токене, одинаковый `404` для отсутствующей и чужой рецензии, `422` при неверном ID или теле запроса, `503` при недоступности БД.

### Удаление пользовательской рецензии

`DELETE /reviews/{review_id}` требует `Authorization: Bearer <jwt>` и принимает положительный внутренний ID рецензии. Тело запроса не требуется. Удалить рецензию может только её автор.

- Успешное удаление возвращает `204` без тела ответа. После удаления автор может снова написать рецензию на тот же фильм.
- Отсутствующая, уже удалённая и чужая рецензия возвращают одинаковый `404`.
- Остальные ошибки: `401` при отсутствующем или недействительном токене, `422` при неверном ID, `503` при недоступности БД.

## Друзья

```http
POST   /friends/requests/{user_id}
GET    /friends/requests
POST   /friends/requests/{request_id}/accept
POST   /friends/requests/{request_id}/reject
DELETE /friends/{user_id}
GET    /friends
```

Все маршруты дружбы доступны без префикса `/api` и требуют `Authorization: Bearer <jwt>`. Текущий пользователь определяется только по токену. `user_id` в пути — UUID другого пользователя, `request_id` — целое число от 1 до 2147483647. Тело запросов не требуется.

### Отправка заявки

`POST /friends/requests/{user_id}` возвращает `201`. Ответ содержит `id`, `user_low_id`, `user_high_id`, `requested_by_id`, `status`, `created_at`, `updated_at`. `status` равен `pending`, `requested_by_id` — ID текущего пользователя. Для каждой пары хранится одна запись с `user_low_id < user_high_id`.

- Заявка самому себе — `400`. Отсутствующий или неактивный получатель — одинаковый `404` с сообщением `Пользователь не найден`.
- Если между участниками уже есть `pending` или `accepted`, возвращается `409` независимо от направления заявки. Встречная заявка не принимает существующую автоматически.
- После `rejected` любой из участников может отправить заявку снова: существующая запись получает `pending`, нового отправителя и новые `created_at`, `updated_at`, ID записи сохраняется. Ответ также `201`.
- Проверка существующей связи и её создание или повторная отправка выполняются атомарно; конкурентные запросы не создают дублей.

### Входящие заявки

`GET /friends/requests?page=1` возвращает только входящие `pending`-заявки текущего пользователя. Исходящие и завершённые заявки не включаются.

- Ответ `200`: `page`, `page_size` (20), `total_results`, `total_pages`, `results`.
- Запись в `results`: `id` заявки, `sender` (объект с `id`, `username`, `avatar_url`), `created_at`.
- Сортировка — по убыванию `created_at`, затем `id`.

### Принятие и отклонение

`POST /friends/requests/{request_id}/accept` и `POST /friends/requests/{request_id}/reject` меняют статус входящей `pending`-заявки на `accepted` или `rejected`. Ответ `200` имеет формат связи из отправки заявки; `updated_at` обновляется, отправитель и время создания сохраняются.

- Изменять заявку может только получатель. Для отправителя, постороннего, отсутствующей и уже обработанной заявки возвращается одинаковый `404`: `Входящая заявка не найдена`.
- Условие получателя и статус проверяются в самом UPDATE. При одновременном принятии и отклонении проходит только один переход.
- Принятие открывает доступ к закрытому профилю друга согласно общим правилам приватности.

### Список и удаление друзей

- `GET /friends?page=1` возвращает только подтверждённых друзей текущего пользователя. Ответ `200`: `page`, `page_size` (20), `total_results`, `total_pages`, `results`. Каждый элемент содержит `id` пользователя, `username`, `avatar_url`. Сортировка — по возрастанию `username`, затем UUID. Email и личные поля профиля не возвращаются.
- `DELETE /friends/{user_id}` удаляет только связь `accepted` текущего пользователя с указанным пользователем и возвращает `204` без тела. Заявки `pending` и `rejected` не удаляются этой операцией. Повторное удаление, отсутствующая и неподтверждённая связь дают одинаковый `404`: `Друг не найден`. Удаление самого себя — `400`. После удаления доступ к закрытым разделам друга прекращается для последующих запросов, новую заявку можно отправить обычным способом.

Для обоих списков `page` принимает значения от 1 до 2147483647, по умолчанию 1. Пустой список возвращает `200` с пустым `results` и нулевыми счётчиками. Страница за пределами выдачи содержит пустой `results` и фактические счётчики. Успешные ответы и прикладные ошибки дружбы используют `Cache-Control: no-store`.

Общие ошибки: `401` при отсутствии или недействительности токена, `422` при неверном UUID, ID заявки или номере страницы, `503` при недоступности БД. Новые изменения схемы БД не требуются. Фронтенд дружбы пока использует имитацию API и подключается к этим маршрутам отдельной задачей.

## Рецензии критиков

```http
GET    /movies/{movie_id}/critic-reviews?language=ru
POST   /admin/critic-reviews
POST   /admin/critic-reviews/import
DELETE /admin/critic-reviews/{review_id}
```

### Ручное добавление

`POST /admin/critic-reviews` доступен без `/api` и требует действующего Bearer-токена пользователя с `role=admin`. Роль читается из БД на каждом запросе, а не принимается из тела или JWT.

Тело запроса:

```json
{
  "movie_id": 7,
  "source_name": "Киноиздание",
  "critic_name": "Иван Иванов",
  "language": "ru",
  "external_url": "https://reviews.example.com/articles/movie-7",
  "title": "Заголовок рецензии",
  "excerpt": "Короткая выдержка из публикации",
  "published_at": "2026-11-26T12:00:00Z"
}
```

- Обязательны `movie_id` (внутренний ID от 1 до 2147483647), `source_name`, `language`, `external_url`, `excerpt`. Строки имени источника, автора, заголовка и выдержки обрезаются по краям, не могут быть пустыми или содержать нулевой символ. Для неизвестного автора `critic_name` пропускается или равен `null`; `title` также необязателен.
- `language` — двухбуквенный код из строчных латинских букв, например `ru` или `en`. `external_url` — абсолютная HTTP/HTTPS-ссылка до 2083 символов без встроенных логина и пароля. Backend нормализует URL, но не загружает публикацию и не извлекает из неё текст автоматически.
- Администратор вводит имя источника и ссылку без предварительного заполнения справочника. Источник `manual` переиспользуется по точному имени после обрезки пробелов и базовому адресу публикации (`scheme://host[:port]/`). Если его нет, создаётся новый. Регистр имени учитывается. Автор переиспользуется по имени внутри источника или создаётся при необходимости. Отсутствующее имя автора не создаёт фиктивного критика. Неактивный источник нельзя использовать для новой рецензии (`409`).
- Оценки и готовые вердикты критиков не используются. Поля `original_score`, `score_scale`, `normalized_score`, `rating` и `verdict` не принимаются и не возвращаются. Их передача, включая null, отклоняется как лишнее поле (`422`). Backend не вычисляет оценку, тональность или вердикт по тексту.
- `published_at` необязателен; при передаче требуется ISO 8601 с часовым поясом. Лишние поля, включая `moderation_status` и `source_id`, отклоняются. Новая рецензия сразу имеет статус `published`, `external_id` остаётся null.
- Ответ `201` содержит `id`, `movie_id`, `source` (`id`, `name`, `website_url`), `critic` (`id`, `name` либо null), `language`, `external_url`, `title`, `excerpt`, `published_at`. Сохранённые старые оценки и вердикты также не раскрываются в ответах.
- Источник, автор и рецензия сохраняются одной транзакцией. Повторная нормализованная ссылка даёт `409`, в том числе для другого фильма, без оставшихся записей справочника от неудачного запроса. Создание одинакового ручного источника и автора сериализуется транзакционной advisory-блокировкой PostgreSQL; схема БД не меняется.

### Публичный просмотр

`GET /movies/{movie_id}/critic-reviews?language=ru&page=1` доступен без `/api` и без токена. Возвращает только `published`-рецензии активных источников для сохранённого фильма.

- `language` необязателен: без него возвращаются все языки, с ним — точное совпадение двухбуквенного кода. `page` — от 1 до 2147483647, по умолчанию 1.
- Ответ `200`: `page`, `page_size` (10), `total_results`, `total_pages`, `results`. Элементы `results` имеют формат ответа создания.
- Сортировка: `published_at` по убыванию, неизвестная дата в конце, затем `id` по убыванию. Пустая выдача — `200` с пустым `results` и нулевыми счётчиками; страница за пределами выдачи сохраняет фактические счётчики.
- Неизвестный фильм — `404`; наличие только скрытых рецензий не раскрывается в счётчиках.

### Удаление и права

`DELETE /admin/critic-reviews/{review_id}` требует роль `admin`; ID — целое от 1 до 2147483647. Успех — `204` без тела, отсутствующая или уже удалённая рецензия — `404`. Источник и автор после удаления остаются в справочниках. Администратор может удалить запись независимо от её статуса публикации.

Общие ошибки: `401` — нет действующего токена для административной операции; `403` — пользователь не администратор; `404` — отсутствующий фильм или удаляемая рецензия; `409` — повторная ссылка или неактивный источник; `422` — некорректные параметры или тело; `503` — недоступна БД. Ответы этих ручек используют `Cache-Control: no-store`; ошибки общих зависимостей и валидации обрабатываются стандартно.

### Импорт из The New York Times

`POST /admin/critic-reviews/import` требует Bearer-токен администратора. Тело: `{"movie_ids": [7, 12]}` — от 1 до 5 различных внутренних ID сохранённых фильмов. Возвращает `200` с `source: "nyt"`, общим `imported` и `results`: для каждого фильма `movie_id`, `fetched`, `imported`, `skipped_existing`, `skipped_unmatched`. Лишние поля запрещены (`422`).

Backend автоматически получает первую страницу (до 10 статей) NYT Article Search API по оригинальному названию и слову review без ограничения даты публикации. Новая рецензия на старый фильм допускается. Импортируется только материал типа Review из раздела Movies с единственным фильмом в тематических тегах, точно совпадающим по нормализованному названию. Год фильма в теге, если есть, должен совпадать с годом выпуска; дата публикации статьи в этой проверке не участвует. Тег без года по-прежнему допускается при совпадении названия, поэтому одноимённые фильмы без года в теге могут быть сопоставлены ошибочно. Фильм без даты выпуска пропускается без обращения к NYT. Это консервативный поиск, а не гарантия наличия рецензии для каждого фильма.

Сохраняются ID статьи, автор, ссылка, заголовок, краткая выдержка и дата; язык `en`, источник типа `api`, статус `published`. Полный текст, изображения, оценки и вердикты не загружаются. Повторные ID и URL пропускаются без обновления существующих рецензий. Ответы содержат счётчики, а не тексты внешних публикаций.

Запросы к NYT разделены паузой минимум 12 секунд в одном процессе backend. Архивный пакет выполняется синхронно. Ошибка NYT, таймаут или лимит запросов — `502` без частичного сохранения архивного пакета; автоматического повторения в ручке нет. Отсутствующий ключ `NYT_API_KEY` — `503`, неактивный источник или изменение фильма во время поиска — `409`, отсутствующий фильм — `404`. Секрет остаётся в backend `.env`. Ручные операции не выполняют scraping. Интерфейс администрирования подключается отдельно.

### Ежедневное обновление NYT

Backend с заданным `NYT_API_KEY` по умолчанию включает APScheduler: запуск ежедневно в 04:00 UTC (07:00 Москвы), час задаётся `NYT_SYNC_HOUR_UTC`. При старте сервера также проверяется необходимость догнать пропущенные дни. Выключение: `NYT_SYNC_ENABLED=false`. Публичной ручки запуска ежедневной задачи нет; архивный POST выше сохраняется.

Первый запуск обрабатывает два последних завершённых дня UTC. Последующие запуски повторно проверяют последний обработанный день и догоняют новые завершённые дни. Это перекрытие помогает при задержке индексации, но не гарантирует обнаружение статей, появившихся в поиске спустя много дней: для них остаётся архивный импорт. Текущий незавершённый день откладывается до следующего запуска. После простоя за один запуск обрабатывается не более 31 дня, остаток — следующими запусками.

Задача читает все страницы публикаций NYT за день и отбирает рецензии раздела Movies на backend. Число HTTP-запросов зависит от числа публикаций, а не от числа фильмов. Без фильтра по году выпуска она находит и новые рецензии на старые фильмы. Сопоставление с сохранёнными фильмами использует нормализованное название и год фильма из тега при его наличии; если подходит несколько фильмов, статья пропускается. Отсутствующий фильм автоматически не создаётся. Статьи с неизвестным фильмом, отсутствующим годом выпуска в каталоге, неподходящими тегами или некорректными полями пропускаются.

Страницы сохраняются транзакционно с существующей защитой от дублей. Дата последнего полностью обработанного дня продвигается только после всех страниц этого дня. При ошибке NYT/БД либо достижении предела API (100 страниц, 1000 статей за день) день не помечается завершённым; следующая задача повторит его без дублей. Исключения записываются безопасным сообщением в журнал, без URL с API-ключом. Задачи разных процессов сериализуются арендой в БД на 30 минут с продлением между страницами; после аварийной остановки аренда истекает. Для соблюдения общего лимита ключа рекомендуется один процесс с включённым расписанием: архивные вызовы в других процессах не разделяют локальную паузу.

## Ошибки

```json
{"detail":{"code":"PRIVATE_PROFILE","message":"Profile data is unavailable"}}
```

Коды: `400`, `401`, `403`, `404`, `409`, `422`, `502`, `503`.

Сервер проверяет права на каждую мутацию. Для закрытого профиля ответы не должны позволять определить существование скрытых данных. Ошибки внешних служб преобразуются в понятный ответ `502`; ключи внешних служб остаются только на сервере.
