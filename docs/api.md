# API-контракт v1

Базовый префикс: `/api`. Формат обмена: JSON. Защищённые методы требуют авторизацию.

`/api` — часть пути запроса, а не сетевой адрес. Адрес backend задаётся настройкой клиентской части; адрес базы данных и ключи внешних служб в браузер не передаются.

## Авторизация

```http
POST /auth/register
POST /auth/login
POST /auth/logout
GET  /auth/me
```

### Текущий этап: PostgreSQL и access JWT

В текущем приложении auth-маршруты доступны без префикса `/api`.

- `POST /auth/register` сохраняет прежний контракт: `username`, `email`, `password`, `password_confirm`; ответ `201` содержит только `username` и `email`. Дубли возвращают `409`, ошибки валидации — `422`.
- Ответ `422` при регистрации содержит массив `detail` с полями `loc`, `msg` и `type` для каждой ошибки. При отсутствии имени пользователя `loc` равно `["body", "username"]`, а `type` — `missing`. Значения из запроса, включая пароль и его подтверждение, в ответ не включаются.
- `POST /auth/login` принимает JSON `{"identifier":"username или email","password":"пароль"}`. Ответ `200`: `{"access_token":"<jwt>","token_type":"bearer"}`. Неверные учётные данные возвращают `401` с одинаковым сообщением; ошибки структуры запроса — `422`.
- Username сравнивается с учётом регистра. Email при входе нормализуется через `EmailStr`, как при регистрации; дополнительного приведения всего адреса к нижнему регистру нет. Пароль не нормализуется.
- `GET /auth/me` требует `Authorization: Bearer <jwt>` и возвращает `id`, `username`, `email`. Пароль и хеш не возвращаются.
- JWT подписывается HS256 и действует 30 минут. Обязательные claims: `sub` (внутренний UUID пользователя), `iat`, `exp`. Проверяются подпись, алгоритм, время и существование пользователя. Недействительный или отсутствующий токен возвращает `401` с `WWW-Authenticate: Bearer`.
- `JWT_SECRET_KEY` задаётся в окружении или `backend/.env`; требуется случайный секрет длиной не менее 32 символов. Значения по умолчанию нет.
- Учётные записи хранятся в `movie_service.users` PostgreSQL. При регистрации пользователь и профиль создаются одной транзакцией; UUID создаётся один раз и сохраняется между перезапусками. UNIQUE-ограничения базы защищают email и username от конкурентных дублей; конфликт возвращает `409`. Приложение не использует `auth.users` Supabase.
- Неактивный пользователь (`is_active=false`) не может войти и не проходит `/auth/me`. При недоступности PostgreSQL зависимые запросы возвращают `503`.
- Refresh token, отзыв JWT и `POST /auth/logout` пока не реализованы. Требование FR.AUTH.05 остаётся отложенным; выданный токен действует до истечения срока, пока существует пользователь и сохраняется ключ подписи.

## Фильмы

```http
GET  /movies?page=1&genre_id=3&year=1999&sort=release_date_desc
GET  /movies/discover?page=1&tmdb_genre_id=28&year=1999&sort=popularity_desc
GET  /movies/search?q=...
GET  /movies/tmdb/{tmdb_id}
GET  /movies/{movie_id}
POST /admin/movies/sync
```

### Локальный каталог

`GET /movies` доступен без `/api` и JWT. Возвращает только фильмы, сохранённые в PostgreSQL.

- `page` — номер страницы от 1 до 2147483647, по умолчанию 1. Размер страницы фиксирован: до 20 фильмов.
- `genre_id` — необязательный внутренний ID жанра (`genres[].id` в карточке), от 1 до 2147483647. `year` — необязательный год выхода от 1 до 9999. При указании обоих фильтров фильм должен подходить под оба.
- `sort` — `release_date_desc` (по умолчанию) или `release_date_asc`. Фильмы без даты идут в конце. При одинаковой дате порядок определяется по возрастанию внутреннего `id`. Сортировка по рейтингу запланирована отдельно.
- Ответ `200` содержит `page`, `page_size` (всегда 20), `total_results` (количество фильмов после фильтрации), `total_pages` и `results` (массив карточек в формате ниже). Если подходящих фильмов нет, `total_results` и `total_pages` равны 0. Страница за пределами выдачи возвращает пустой `results` с фактическими общими счётчиками.
- Ошибки: `422` при неверных параметрах, `503` при недоступности базы данных.

### Витрина TMDB

`GET /movies/discover` доступен без `/api` и JWT. Backend запрашивает `/discover/movie` в TMDB. PostgreSQL для витрины не используется.

- `page` — от 1 до 500, по умолчанию 1. Размер страницы задаёт TMDB.
- `tmdb_genre_id` — необязательный внешний ID жанра (из `genre_ids` в выдаче TMDB), от 1 до 2147483647. `year` — необязательный год основного релиза от 1 до 9999. Оба фильтра можно применять вместе.
- `sort` — `popularity_desc` (по умолчанию), `release_date_asc` или `release_date_desc`.
- Ответ `200` имеет тот же формат, что и поиск. `total_pages` ограничен 500, `total_results` показывает общее число совпадений по данным TMDB. При отсутствии совпадений `results` пуст.
- Ошибки: `422` при неверных параметрах, `502` при сбое TMDB или некорректном ответе, `503` при отсутствии настройки TMDB.

### Поиск и открытие фильма

Реализованные маршруты доступны без `/api`, публично, без JWT:

- `GET /movies/search?q=Матрица&page=1` обращается к TMDB, не читает и не изменяет БД. `q` после удаления пробелов по краям содержит 1–200 символов; `page` — 1–500. Ответ 200: `page`, `total_pages`, `total_results`, `results`. Каждый результат содержит `tmdb_id`, `title`, `original_title`, `overview`, `release_date`, `poster_path`, `original_language`, `genre_ids`; необязательные текстовые поля и дата допускают null. `genre_ids` — внешние ID TMDB. Пустая выдача — 200 с пустым массивом.
- `GET /movies/tmdb/{tmdb_id}` открывает выбранный результат витрины или поиска: возвращает локальную карточку, если фильм уже есть; иначе получает подробности TMDB и сохраняет фильм, жанры и связи одной транзакцией. Успешный ответ имеет статус 200. Повторные и конкурентные открытия не создают дублей и не перезаписывают существующую карточку. Сохранение является внутренним наполнением кеша каталога, не правом редактирования фильма.
- `GET /movies/{movie_id}` читает карточку только по внутреннему ID из PostgreSQL, без обращения к TMDB. Неизвестный ID — 404.
- Карточка: `id` (внутренний), `tmdb_id`, `title`, `original_title`, `overview`, `release_date`, `poster_path`, `runtime`, `original_language`, `genres` (массив объектов `id`, `tmdb_id`, `name`). Неизвестная длительность, включая 0 от TMDB, возвращается как null. Путь постера не является полным URL. Все ID в пути — целые 1–2147483647.
- Для оценок, списков, рецензий и маршрута frontend `/movies/:id` используется внутренний `id` из карточки, а не `tmdb_id` поиска.
- Ответы `GET /movies/{movie_id}` и `GET /movies/tmdb/{tmdb_id}` дополнительно содержат `average_rating` (средняя оценка пользователей Movie Service по шкале от 1 до 10, округлённая до двух знаков) и `ratings_count` (количество оценок). Оценки закрытых профилей входят в агрегат анонимно. При отсутствии оценок `average_rating` равен `null`, а `ratings_count` равен `0`.
- В этих же ответах `tmdb_vote_average` (число от 0 до 10 с точностью до трёх знаков), `tmdb_vote_count` (число голосов) и `tmdb_rating_updated_at` (время сохранения в ISO 8601) показывают сохранённые данные TMDB. У ранее сохранённых фильмов и при отсутствии данных TMDB все три поля равны `null`. Если TMDB сообщает о нуле голосов, `tmdb_vote_count` равен `0`, `tmdb_vote_average` равен `null`, а время сохранения заполнено. Данные записываются при первом сохранении фильма.
- Ошибки: 422 — неверные параметры; 404 — фильм отсутствует или относится к adult-контенту; 502 — сбой TMDB или некорректные данные; 503 — отсутствует настройка TMDB либо недоступна БД. Сохранённая карточка доступна без токена и при сбое TMDB. Поиск по-прежнему требует доступного TMDB.

Административная синхронизация остаётся отдельным этапом. Автоматическое обновление сохранённых карточек и кеширование поисковой выдачи пока не реализованы.

## Пользователи и профили

```http
GET   /users/{username}
PATCH /users/me/profile
GET   /users/{username}/movies?list_type=watched
GET   /users/{username}/ratings
GET   /users/{username}/reviews
```

В закрытом профиле списки `watchlist`, `watched`, `favorite`, история оценок и полный список рецензий доступны владельцу и подтверждённым друзьям. Остальные посетители видят только `username` и аватар. Ответы профильных запросов не раскрывают содержимое, количество и наличие скрытых записей.

`GET /users/{username}/ratings` — запланированный маршрут для истории оценок.

## Списки, оценки и рецензии

```http
POST   /movies/{movie_id}/lists          # {"list_type":"watchlist"}
DELETE /movies/{movie_id}/lists/{list_type}
PUT    /movies/{movie_id}/rating         # {"score":8}
DELETE /movies/{movie_id}/rating
GET    /movies/{movie_id}/reviews
POST   /movies/{movie_id}/reviews        # {"text":"...","contains_spoilers":false}
PATCH  /reviews/{review_id}
DELETE /reviews/{review_id}
```

### Оценки фильмов

`PUT` и `DELETE /movies/{movie_id}/rating` доступны без префикса `/api` и требуют `Authorization: Bearer <jwt>`. `movie_id` — внутренний ID сохранённого фильма. Операции используют ID пользователя из токена.

- `PUT` принимает `{"score":8}`. `score` — строго целое число от 1 до 10. Запрос создаёт оценку или заменяет значение существующей оценки текущего пользователя. В обоих случаях ответ `200` содержит `movie_id` и `score`.
- `DELETE` удаляет оценку текущего пользователя. Ответ `204` без тела возвращается и при повторном удалении, если фильм существует.
- Ошибки: `401` при отсутствующем или недействительном токене, `404` если фильм не сохранён, `422` при неверном ID фильма или теле запроса `PUT`, `503` при недоступности БД.

### Просмотр пользовательских рецензий на фильм

`GET /movies/{movie_id}/reviews` возвращает опубликованные рецензии на сохранённый фильм по его внутреннему ID. Маршрут доступен без префикса `/api` и без токена. Рецензии авторов с закрытыми профилями входят в выдачу на общих основаниях. Правила доступа к спискам в профиле применяются к запросам `/users/{username}/...`.

- Параметр `page` задаёт номер страницы от 1 до 2147483647. По умолчанию возвращается первая страница. Размер страницы фиксирован и составляет до 10 рецензий.
- Ответ `200` содержит объект с полями `page`, `page_size` (всегда 10), `total_results` (общее количество рецензий фильма), `total_pages` и `results` (массив рецензий текущей страницы).
- Каждая запись в `results` включает `id`, `movie_id`, `text`, `contains_spoilers`, `created_at` и `author_username`. Рецензии отсортированы от новых к старым по `created_at`, при совпадении времени — по убыванию `id`.
- Для фильма без рецензий возвращается `200` с пустым `results` и нулевыми счётчиками `total_results` и `total_pages`. Страница за пределами выдачи возвращает пустой `results` с фактическими общими счётчиками.
- Ошибки — `404`, если фильм не сохранён, `422` при неверном ID фильма или номере страницы, `503` при недоступности БД.

### Создание пользовательской рецензии

`POST /movies/{movie_id}/reviews` доступен без префикса `/api` и требует `Authorization: Bearer <jwt>`. `movie_id` — внутренний ID сохранённого фильма. Автор определяется по токену. Выставлять оценку перед созданием рецензии не требуется.

- Тело запроса содержит `text` с текстом рецензии и необязательный булев `contains_spoilers` (по умолчанию `false`). Текст должен содержать хотя бы один непробельный символ и не может содержать нулевой символ. Лишние поля отклоняются.
- Ответ `201` содержит `id`, `movie_id`, `text`, `contains_spoilers` и `created_at`.
- Ошибки: `401` при отсутствующем или недействительном токене, `404` если фильм не сохранён, `409` если текущий пользователь уже написал рецензию на этот фильм, `422` при неверном ID или теле запроса, `503` при недоступности БД.

### Редактирование пользовательской рецензии

`PATCH /reviews/{review_id}` доступен без префикса `/api` и требует `Authorization: Bearer <jwt>`. `review_id` — положительный внутренний ID рецензии. Редактирование доступно только автору, включая владельца закрытого профиля.

- Тело содержит `text`, `contains_spoilers` или оба поля. Пропущенные поля сохраняют прежние значения. Пустой объект, `null` и лишние поля отклоняются. Правила текста и булева флага совпадают с созданием рецензии.
- Ответ `200` содержит `id`, `movie_id`, `text`, `contains_spoilers`, `created_at` и `updated_at`. Обновляется существующая запись с сохранением автора, фильма и времени создания.
- Ошибки: `401` при отсутствующем или недействительном токене, одинаковый `404` для отсутствующей и чужой рецензии, `422` при неверном ID или теле запроса, `503` при недоступности БД.

### Удаление пользовательской рецензии

`DELETE /reviews/{review_id}` требует `Authorization: Bearer <jwt>` и принимает положительный внутренний ID рецензии. Тело запроса не требуется. Удалить рецензию может только её автор.

- Успешное удаление возвращает `204` без тела ответа. После удаления автор может снова написать рецензию на тот же фильм.
- Отсутствующая, уже удалённая и чужая рецензия возвращают одинаковый `404`.
- Остальные ошибки: `401` при отсутствующем или недействительном токене, `422` при неверном ID, `503` при недоступности БД.

## Ошибки

```json
{"detail":{"code":"PRIVATE_PROFILE","message":"Profile data is unavailable"}}
```

Коды: `400`, `401`, `403`, `404`, `409`, `422`, `502`, `503`.

Сервер проверяет права на каждую мутацию. Для закрытого профиля ответы не должны позволять определить существование скрытых данных. Ошибки внешних служб преобразуются в понятный ответ `502`; ключи внешних служб остаются только на сервере.
