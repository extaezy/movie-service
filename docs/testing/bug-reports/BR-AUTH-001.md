# BR-AUTH-001 — Пароль возвращается в ошибке регистрации без username

| Поле | Значение |
|---|---|
| Дата обнаружения | 07.11.2026 |
| Дата оформления | 08.11.2026 |
| Статус | Новый, требуется рассмотрение командой |
| Тип | Замечание безопасности |
| Компонент | `POST /auth/register`, ошибки валидации |
| Серьёзность | Не назначена; требуется оценка последствий |
| Приоритет | Не назначен; требуется решение команды |
| Связи | [TC-AUTH-REG-004-01](../test-cases/TC-AUTH-REG-004-01.md), [QA-SEC-002](../findings.md#qa-sec-002), AUTH-Q-003 |

## Окружение

- Ветка: `test`. Коммит: `e72c3797f8c42c3134531eb075311c97faea5223`.
- Windows, Python 3.13.17, FastAPI.
- Backend: `http://127.0.0.1:8000`; запрос выполнен через Swagger UI.
- Отдельная PostgreSQL в Docker: образ `postgres:17`, контейнер `movie-service-test-db`, БД `movie_service_test`, миграция `20261101_0001`.

## Предусловия

Backend запущен с настройками отдельной тестовой БД. Доступна страница `http://127.0.0.1:8000/docs`. Авторизация для регистрации не требуется.

## Шаги воспроизведения

1. Открыть Swagger UI, выбрать `POST /auth/register` и нажать `Try it out`.
2. Вставить JSON без username. Здесь используется вымышленный тестовый пароль:

```json
{
  "email": "qa.required@example.com",
  "password": "testing-password-123",
  "password_confirm": "testing-password-123"
}
```

3. Нажать `Execute`.
4. Проверить поля `password` и `password_confirm` в `detail[].input` ответа.

## Фактический результат

HTTP `422`. Ответ из ручного прогона:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "username"],
      "msg": "Field required",
      "input": {
        "email": "qa.required@example.com",
        "password": "testing-password-123",
        "password_confirm": "testing-password-123"
      }
    }
  ]
}
```

Ответ повторяет введённые пароль и подтверждение в открытом виде. Наблюдение подтверждено ручными запросами 07.11.2026 и 08.11.2026 на том же коммите. При повторном прогоне также проверена БД: до и после запроса по одному пользователю и профилю; пользователя с тестовым email нет.

## Ожидаемый результат

HTTP `422` сохраняется, ошибка указывает на обязательный username. Значения `password` и `password_confirm` не повторяются в ответе. Допустимый способ исключения чувствительных данных из ответа необходимо согласовать с командой.

Основание ожидания — предлагаемое требование безопасности к составу ошибок. Действующий [API-контракт](../../api.md#текущий-этап-postgresql-и-access-jwt) определяет статус `422`, но не закрепляет безопасный состав ошибок валидации. Этот вопрос связан с AUTH-Q-003; согласованная спецификация этим отчётом не изменяется.

## Влияние и границы подтверждения

Повторное присутствие пароля в ответе увеличивает риск его попадания в сохраняемые тела ответов, отчёты и системы диагностики. Такое сохранение в этом прогоне не проверялось.

Подтверждено отражение данных самого запроса. Получение чужих паролей, хешей или доступа к учётным записям не продемонстрировано. Основание для оценки — [CWE-209: чувствительная информация в сообщениях об ошибках](https://cwe.mitre.org/data/definitions/209.html); окончательная классификация и серьёзность требуют рассмотрения командой.

## Критерии повторной проверки

- На таком же запросе получен `422` с понятной причиной отказа по username.
- В теле ответа отсутствуют отправленные значения пароля и подтверждения, в том числе во вложенных объектах.
- Проверены другие согласованные варианты ошибок валидации auth на аналогичное отражение.

Решение команды, исполнитель и исправление пока не зафиксированы. Функциональный кейс TC-AUTH-REG-004-01 пройден 08.11.2026 с SQL-проверками до и после запроса; замечание безопасности при этом воспроизведено повторно и остаётся открытым.
