## Предусловия

Backend запущен с настройками отдельной тестовой БД. Доступна страница `http://127.0.0.1:8000/docs`. Авторизация для регистрации не требуется.

## Шаги воспроизведения

1. Открыть Swagger UI, выбрать `POST /auth/register` и нажать `Try it out`.
2. Вставить JSON без username. Здесь используется вымышленный тестовый пароль:

```json
{
  "email": "qa.required@example.com",
  "password": "testing-password-123",
  "password_confirm": "testing-password-123"
}
```

3. Нажать `Execute`.
4. Проверить поля `password` и `password_confirm` в `detail[].input` ответа.

## Фактический результат

HTTP `422`. Ответ из ручного прогона:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "username"],
      "msg": "Field required",
      "input": {
        "email": "qa.required@example.com",
        "password": "testing-password-123",
        "password_confirm": "testing-password-123"
      }
    }
  ]
}
```

Ответ повторяет введённые пароль и подтверждение в открытом виде. Наблюдение подтверждено ручными запросами 07.11.2026 и 08.11.2026 на том же коммите. При повторном прогоне также проверена БД: до и после запроса по одному пользователю и профилю; пользователя с тестовым email нет.

## Ожидаемый результат

HTTP `422` сохраняется, ошибка указывает на обязательный username. Значения `password` и `password_confirm` не повторяются в ответе. Допустимый способ исключения чувствительных данных из ответа необходимо согласовать с командой.

На момент обнаружения основанием ожидания было предлагаемое требование безопасности к составу ошибок. API-контракт определял статус `422`, но не закреплял безопасный состав ошибок валидации. После слияния `test` актуальный [API-контракт](../../api.md#текущий-этап-postgresql-и-access-jwt) явно требует `loc`, `msg`, `type` без значений запроса для ошибок регистрации. Историческое наблюдение ниже сохранено; результат повторной проверки приведён в конце.

## Влияние и границы подтверждения

Повторное присутствие пароля в ответе увеличивает риск его попадания в сохраняемые тела ответов, отчёты и системы диагностики. Такое сохранение в этом прогоне не проверялось.

Подтверждено отражение данных самого запроса. Получение чужих паролей, хешей или доступа к учётным записям не продемонстрировано. Основание для оценки — [CWE-209: чувствительная информация в сообщениях об ошибках](https://cwe.mitre.org/data/definitions/209.html); окончательная классификация и серьёзность требуют рассмотрения командой.

## Критерии повторной проверки

- На таком же запросе получен `422` с понятной причиной отказа по username.
- В теле ответа отсутствуют отправленные значения пароля и подтверждения, в том числе во вложенных объектах.
- Проверены другие согласованные варианты ошибок валидации auth на аналогичное отражение.

На 08.11.2026 решение команды и исправление ещё не были зафиксированы. Функциональный кейс TC-AUTH-REG-004-01 был пройден с SQL-проверками до и после запроса; замечание безопасности тогда воспроизвелось повторно.

## Повторная проверка 15.11.2026

Проверена рабочая копия поверх `83c24ef` после слияния `origin/test` на `0472125`. В текущем `app.main` обработчик ошибок регистрации формирует только `loc`, `msg`, `type`. Проверка выполняется через настоящее приложение и PostgreSQL в `movie_service_automation_test` с миграцией `20261113_0002`.

Добавлен `test_registration_validation_errors_do_not_expose_input` в `backend/tests/test_postgres_integration.py`: восемь вариантов — отсутствие каждого обязательного поля, неверный email, короткий пароль, несовпадение подтверждения и объект с вложенным маркером вместо пароля. Во всех случаях получен 422, массив ошибок непустой, каждая ошибка содержит ровно `loc`, `msg`, `type`; переданные строковые значения и вложенный маркер не отражены. Для отсутствующих полей проверены точные `loc` и `type=missing`. Пользователи и профили не созданы.

Восемь вариантов прошли в целевом прогоне **51 passed, 100 deselected in 1.86s** вместе с каталогом. Полный backend-набор: **241 passed, 1 skipped, 1 xfailed in 23.30s**; Ruff прошёл. Skip — отдельный smoke, xfail — BR-MOV-001.

Исходный дефект регистрации в проверенных вариантах не воспроизводится. Вход, журналирование, интерфейс Swagger и другие маршруты на отражение значений этим тестом не проверяются. Статусы задач во внешнем taskboard не менялись.
