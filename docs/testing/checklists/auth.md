# Ручная проверка авторизации

Назначение — проверить интерфейс и взаимодействие frontend/backend после изменений соответствующих экранов. Автоматизированные варианты API перечислены в [матрице](../coverage.md); повторять всю таблицу входных данных вручную при каждом прогоне не требуется.

Нужны запущенные frontend/backend и отдельная тестовая БД. Используются вымышленные свободные email и username. Для каждого условия фиксируется фактический результат и обнаруженные проблемы.

| ID | Действие | Ожидаемый результат |
|---|---|---|
| AUTH-UI-001 | Зарегистрироваться через /register, затем войти | Успех регистрации виден пользователю; вход открывает авторизованный интерфейс |
| AUTH-UI-002 | Отправить форму с ошибочным полем, затем с занятым username/email | Ошибка отображается понятно, форма позволяет исправить данные; пароль не появляется в сообщении |
| AUTH-UI-003 | Войти по username, затем по email | Оба предусмотренных способа доступны через интерфейс |
| AUTH-UI-004 | Передать неверный пароль | Показана ошибка; авторизованный интерфейс не открывается |
| AUTH-UI-005 | Задержать ответ регистрации/входа, затем смоделировать ошибку сервера | Видно ожидание, кнопка заблокирована; после отказа видна ошибка и можно повторить запрос |
| AUTH-UI-006 | Войти последовательно двумя тестовыми пользователями | Отображаемая учётная запись соответствует текущему входу; данные прежнего пользователя не остаются |

FR.AUTH.05 и отзыв JWT отложены в действующем API и не объявляются проверенными этим чек-листом. Полный профиль и приватность требуют отдельных проверок FR.USER.*.
