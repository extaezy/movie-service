# Чек-лист регистрации, входа и текущего пользователя

Дата подготовки — 07.11.2026. Статус документа — черновик для совместного ревью с QA.

Базовая ветка — `test`. Базовый коммит — `e72c3797f8c42c3134531eb075311c97faea5223`.

Область проверки — `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, связанное хранение пользователей и профилей. На этом этапе маршруты доступны без `/api`. Отзыв токена при выходе отложен в API-документации.

AUTH-REG-001, AUTH-REG-002, AUTH-REG-003, AUTH-REG-007, AUTH-REG-008, AUTH-LOGIN-001, AUTH-LOGIN-002, AUTH-LOGIN-003, AUTH-ME-001, AUTH-ME-002 и AUTH-ME-003 пройдены вручную 07.11.2026; подробности приведены под соответствующими таблицами. AUTH-REG-005 и AUTH-ME-012 пройдены автоматически 08.11.2026; результаты приведены в разделе автоматизированного прогона ниже. Остальные строки имеют результат «Не выполнено», включая частично выполненную AUTH-REG-004. Результаты исторических прогонов тестов разработчика не перенесены в этот чек-лист.

AUTH-REG-004 выполняется частично: вариант без username пройден 08.11.2026 вручную с SQL-проверками и автоматически. Отсутствие email также проверено автотестом. Итоговый статус этой строки остаётся «Не выполнено» до проверки остальных вариантов и отсутствия новых записей в БД для них.

## Источники и обозначения

Ожидаемые результаты основаны на основном тексте требований, описании текущего этапа API и документации БД. Условия, найденные только в реализации, вынесены в отдельный раздел для согласования. Исходная версия документов закреплена базовым коммитом. [Требования](../../requirements.md) · [API](../../api.md) · [БД](../../database.md) · [Зафиксированная версия проекта](https://github.com/extaezy/movie-service/tree/e72c3797f8c42c3134531eb075311c97faea5223)

`AUTH-REG-*`, `AUTH-LOGIN-*`, `AUTH-ME-*`, `AUTH-TOKEN-*`, `AUTH-DATA-*` и `AUTH-SEC-*` — внутренние ID проверок QA. `AUTH-P-*` — предварительные проверки. `AUTH-Q-*` — открытые вопросы. Связь с существующими ID требований приведена в матрице. [Матрица покрытия](../coverage.md)

В основном тексте требований отсутствуют отдельные `BRULE.AUTH.*`. Правила уникальности относятся к `FR.AUTH.02`, атомарность создания пользователя и профиля описана в API-контракте.

## Условия выполнения

- Подготовлена отдельная тестовая PostgreSQL, на которую применены миграции проверяемого коммита.
- Backend использует настройки этой тестовой базы и отдельный тестовый JWT-секрет.
- `baseUrl` содержит фактический адрес запущенного backend. Значение фиксируется при прогоне.
- Исходные данные для каждой проверки подготовлены независимо от порядка выполнения остальных строк.
- Остановка БД, деактивация аккаунтов, удаление записей и внедрение ошибок выполняются в изолированном тестовом окружении.
- Для проверки записи в БД доступен SQL-клиент либо отдельная тестовая сессия.

Для ручного прогона 07.11.2026 подготовлена отдельная локальная PostgreSQL в Docker и запущен backend с подключением к ней. Дата, окружение, проверяемый коммит и результаты приведены в записи ручного прогона под таблицей регистрации.

## Тестовые данные

Базовый запрос регистрации использует вымышленные данные. Для каждого независимого запуска выбираются свободные username и email.

```json
{
  "username": "qa_alpha",
  "email": "qa.alpha@example.com",
  "password": "testing-password-123",
  "password_confirm": "testing-password-123"
}
```

Пользователь A — `qa_alpha`, `qa.alpha@example.com`. Пользователь B — `qa_beta`, `qa.beta@example.com`. В проверках доступа пользователи получают собственные токены. В проверках дублей сохраняется только то поле, уникальность которого проверяется. При проверке границ остальные поля корректны, username и email свободны.

В строках с несколькими вариантами каждый вариант выполняется отдельно. Итог «Пройдено» устанавливается после проверки всех перечисленных вариантов. При частичном выполнении в отчёте перечисляются фактически проверенные значения.

## JWT и текущий пользователь

Для отрицательных проверок JWT формируется тестовый токен с одним изменённым условием. При проверке claims и срока подпись должна быть корректной для тестового окружения. Все остальные условия сохраняются корректными. Простое чтение содержимого JWT используется вместе с запросом `/auth/me`, проверяющим принятие токена приложением.

| ID | Действие и данные | Ожидаемый результат | Основание | Результат |
|---|---|---|---|---|
| AUTH-TOKEN-001 | Проверить токен успешного входа и вызвать с ним `/auth/me` | Алгоритм HS256. Присутствуют `sub`, `iat`, `exp`. `sub` соответствует UUID пользователя, `exp - iat = 1800` секунд, время выдачи соответствует времени входа. `/auth/me` принимает токен | FR.AUTH.04, NFR.SEC.05, API | Не выполнено |
| AUTH-ME-001 | Вызвать `/auth/me` с действующим токеном A | `200`. Только поля `id`, `username`, `email`, значения принадлежат A | API, частично FR.USER.01 | Пройдено |
| AUTH-ME-002 | Вызвать `/auth/me` без Authorization | `401` и заголовок `WWW-Authenticate: Bearer` | NFR.SEC.02, API | Пройдено |
