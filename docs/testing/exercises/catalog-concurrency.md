## Новая тема — управление порядком выполнения

`asyncio.gather` запускает запросы конкурентно, но сам по себе не гарантирует, что оба запроса увидят отсутствие фильма. Один может успеть сохранить карточку до проверки второго. Тогда тест проверит обычное чтение кеша.

`asyncio.Barrier(2)` задерживает первую задачу на `await barrier.wait()`, пока вторая не дойдёт до такого же вызова. Обе продолжают работу после встречи. В нашем тесте барьер ставится в подменённом HTTP-ответе TMDB: к этому моменту каждый запрос уже проверил локальную БД и не нашёл фильм, но ещё не начал сохранение. Так гарантированно проверяется повторная попытка вставки одного tmdb_id; точный порядок SQL-вставок остаётся свободным.

`asyncio.wait_for(operation, timeout=5)` ограничивает ожидание. Если второй участник не дошёл до барьера, тест завершится с TimeoutError. При таймауте операция отменяется; завершение отмены может занять дополнительное время. Это ограничение ожидания теста, не требование к производительности backend. `sleep` для синхронизации не нужен.

Справка: [Barrier в Python 3.13](https://docs.python.org/3.13/library/asyncio-sync.html#asyncio.Barrier), [wait_for](https://docs.python.org/3.13/library/asyncio-task.html#asyncio.wait_for).

## Три примера

Две задачи встречаются в одной точке:

```python
barrier = asyncio.Barrier(2)

async def participant(name):
    await barrier.wait()
    return name

results = await asyncio.gather(participant("first"), participant("second"))
```

Асинхронный обработчик подменённого TMDB может приостановить ответ. `payload` и `barrier` создаются внутри теста:

```python
async def upstream(request):
    await barrier.wait()
    return httpx.Response(200, json=payload)

catalog_tmdb.use_upstream(upstream)
```

Ограничение ожидания охватывает всю пару запросов:

```python
responses = await asyncio.wait_for(
    asyncio.gather(client.get(endpoint), client.get(endpoint)),
    timeout=timeout_seconds,
)
```

Последовательные `await client.get(...)` с барьером не подойдут: первый запрос будет ждать второго, который ещё не запущен.

## Готовая инфраструктура

Добавляй тесты в `backend/tests/test_postgres_integration.py`: нужные импорты, маркер asyncio и фикстуры там уже есть.

| Объект | Назначение |
|---|---|
| client | HTTP-клиент настоящего приложения, без подмены репозитория |
| database.sessions() | Новая сессия PostgreSQL для проверки зафиксированных записей |
| catalog_tmdb.use_upstream(handler) | Подмена только внешнего HTTP; принимает синхронный или асинхронный обработчик |
| catalog_tmdb.upstream_requests | Список отправленных запросов; запрос добавляется до входа в handler |
| tmdb_details_payload | Новый словарь корректной карточки для каждого теста |

Не разделяй одну AsyncSession между конкурентными запросами. Приложение создаёт сессию для каждого запроса, проверка БД выполняется отдельной сессией после завершения обоих.

## Задание 1 — один фильм, две версии карточки

Проверка MOV-DB-007. Два запроса открывают один tmdb_id, но получают разные названия и жанры. Победитель заранее неизвестен. Результатом должна стать одна целая карточка одного из ответов TMDB; смешивать название первой версии и жанр второй нельзя.

Каркас содержит подготовленные данные; реализацию обработчика, запросов и assertions добавь самостоятельно:

```python
async def test_concurrent_movie_imports_keep_one_card(
    client, database, catalog_tmdb, tmdb_details_payload
):
    endpoint = "/movies/tmdb/603"
    request_count = 2

        {

            "title": "Первая версия",

        },
        {
            **tmdb_details_payload,
            "title": "Вторая версия",
            "genres": [{"id": 18, "name": "Драма"}],
        },
    ]
    expected_status = 200
    expected_movie_count = 1
    expected_genre_count = 1
    expected_link_count = 1

    ...
```

1. Напиши `async def upstream(request)`. Выбери payload по индексу `len(catalog_tmdb.upstream_requests) - 1` до первого await, затем дождись барьера и верни HTTP 200 с выбранной карточкой. Если выбирать индекс после барьера, оба обработчика могут взять последний payload.
2. Подключи обработчик и отправь два запроса через gather с ограничением ожидания.
3. Проверь два статуса 200, полное равенство JSON и ровно два обращения к TMDB.
4. Установи, какая версия победила по title. Проверь, что единственный жанр соответствует именно этой версии.
5. В новой сессии проверь количество всех трёх видов записей, данные фильма и жанра, связь `(movie_id, genre_id)` и соответствие ID ответу API. Не ожидай конкретного значения внутреннего ID: конфликт или откат может расходовать значения sequence.
6. Замени обработчик на функцию, вызывающую `pytest.fail`, и прочитай карточку ещё раз. Ожидаются тот же JSON и прежние два обращения к TMDB. Старый обработчик с барьером нельзя оставлять для одиночного запроса: при ошибке кеширования он зависнет в ожидании пары.

## Промежуточный результат задания 1

Первый этап выполнен: два запроса используют асинхронный обработчик, выбирают разные payload до барьера и получают 200. Отдельный прогон дал **1 passed, 55 deselected in 0.41s**.

Знакомые проверки дополнены автоматически: полное равенство JSON, два внешних запроса, один фильм, один жанр и одна связь в новой сессии; соответствие записей ответу API; повторное открытие из кеша с запретом внешнего вызова. Блок каталога после дополнения дал **11 passed, 45 deselected in 1.06s**. Это промежуточная проверка, задание ещё не завершено.

На промежуточном этапе требовалось проверить согласованность исходной версии: итоговые title, tmdb_id жанра и name жанра должны вместе соответствовать одному payload. Равенство двух HTTP-ответов и соответствие БД этим ответам ещё допускают одинаковую ошибку во всех трёх местах.

Кортеж объединяет несколько значений в одно сравниваемое значение:

```python
version = ("Учебный фильм", 878, "Фантастика")
```

Оператор `in` ищет совпадение целого кортежа с одним из элементов списка:

```python
allowed_versions = [
    ("Фильм A", 28, "Боевик"),
    ("Фильм B", 18, "Драма"),
]
assert ("Фильм A", 28, "Боевик") in allowed_versions
assert ("Фильм A", 18, "Драма") not in allowed_versions
```

Во входном payload внешний ID жанра называется id; в карточке backend тот же внешний ID называется tmdb_id. Поле id жанра в ответе backend — внутренний ключ PostgreSQL. Например:

```python
payload_genre_id = payloads[0]["genres"][0]["id"]
card_genre_tmdb_id = first_card["genres"][0]["tmdb_id"]
```

Завершающий шаг задания: собери из payloads список допустимых кортежей `(title, внешний ID жанра, name жанра)`, собери такой же кортеж из first_card и проверь его вхождение в список. Список можно заполнить обычным циклом и append или списковым включением. Не фиксируй победу первой или второй версии. Переменные для этого этапа:

```python
allowed_versions = []
actual_version = ()
```
