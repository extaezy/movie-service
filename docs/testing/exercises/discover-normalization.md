# Практика сравнения связанных ответов витрины

Подготовлено 15.11.2026, рабочая копия поверх `83c24ef`, ветка `feature/backend-qa-tests`. Задание MOV-DISC-008 завершено: `test_discover_ignores_unknown_upstream_fields` находится в `backend/tests/test_movies_api.py`. Каркас и инструкции ниже сохранены как учебный материал.

## Что проверяет витрина

`GET /movies/discover` получает страницу фильмов через TMDB и возвращает согласованный JSON. Внешний HTTP подменяется, а настоящий роутер, клиент TMDB и Pydantic-нормализация выполняются. PostgreSQL для этого маршрута не нужен.

Уже написаны проверки публичного доступа, преобразования параметров, границ, пустой выдачи, ограничения total_pages, ответов 422/502/503, безопасности ошибок и следующего успешного запроса после ConnectError. Отдельный outage-сценарий проверяет витрину во время остановки собственного тестового PostgreSQL.

## Новая идея: сравнивать связанные запросы

Можно проверять каждый ответ отдельно по заранее известному JSON. Другой полезный приём — изменить входные данные контролируемым способом и проверить ожидаемую связь между ответами. Такой подход называют метаморфным тестированием.

В этом задании добавляем неизвестное поле во внешний JSON, сохраняя все согласованные поля. Наш API должен вернуть прежний нормализованный результат: клиенту нужны поля из контракта, дополнительные сведения провайдера в ответ не входят. Основание — [формат витрины](../../api.md#витрина-tmdb) и существующая нормализация `TMDBSearchResult` / `TMDBMovie`.

Проверяем три случая:

| Изменение ответа TMDB | Ожидание |
|---|---|
| Добавлено поле на уровне страницы | JSON backend совпадает с исходным нормализованным ответом |
| Добавлено поле внутри первого фильма | JSON backend совпадает с исходным нормализованным ответом |
| Добавлены оба поля | JSON backend совпадает с исходным нормализованным ответом |

Исходный ответ также сравнивается с `tmdb_search_expected_json`. Это защищает от ситуации, когда оба запроса одинаково возвращают неправильный результат. Если удалено обязательное поле, ожидание другое — 502; такие сценарии уже сгенерированы.

## Зачем deepcopy

Обычное присваивание связывает два имени с одним объектом. Поверхностная копия создаёт новый внешний словарь, сохраняя ссылки на вложенные объекты. `deepcopy` копирует и вложенные словари и списки, позволяя менять тестовые данные независимо. Она принимает исходный объект и возвращает его глубокую копию. Для обычного JSON достаточно одного аргумента. [Документация Python 3.13](https://docs.python.org/3.13/library/copy.html).

Пример 1 — присваивание:

```python
original = {"page": 2}
changed = original
changed["page"] = 3
assert original["page"] == 3
```

`changed` и `original` указывают на один словарь, поэтому изменение видно через оба имени.

Пример 2 — поверхностная копия:

```python
original = {"page": 2, "results": [{"id": 603}]}
changed = original.copy()
changed["page"] = 3
changed["results"][0]["id"] = 604
assert original["page"] == 2
assert original["results"][0]["id"] == 604
```

Внешние словари разные, а вложенные список и словарь фильма общие.

Пример 3 — глубокая копия:

```python
from copy import deepcopy

original = {"page": 2, "results": [{"id": 603}]}
changed = deepcopy(original)
changed["results"][0]["id"] = 604
assert original["results"][0]["id"] == 603
assert changed["results"][0]["id"] == 604
```

Для JSON-структуры в этом примере вложенные данные независимы. В тестовом файле импорт `deepcopy` уже добавлен.

## Какие фикстуры использовать

- `tmdb_search_payload` — сырой JSON провайдера: внешний ID фильма записан в поле `id`.
- `tmdb_search_expected_json` — ожидаемый JSON нашего API: внешний ID находится в `tmdb_id`; все остальные согласованные поля заполнены.
- `movie_api.use_upstream(handler)` — задаёт обработчик внешнего HTTP. После вызова можно отправить запрос через `movies_client`.
- `movie_api.upstream_requests` — общая история запросов в рамках теста. Повторный вызов `use_upstream` меняет обработчик, сохраняя историю.
- `movie_api.database_calls` и моки репозиториев позволяют проверить отсутствие работы с БД.

Обработчик из знакомых тестов можно использовать два раза: сначала вернуть `base_payload`, затем переключить его на `extended_payload`. Каждый запрос должен выполняться после установки соответствующего обработчика.

## Каркас MOV-DISC-008

Вставь в конец `backend/tests/test_movies_api.py`. Все импорты уже есть. Каркас объявляет параметры и данные; изменение payload, HTTP-запросы и assertions нужно написать самостоятельно.

```python
@pytest.mark.parametrize(
    "add_page_field, add_movie_field",
    [(True, False), (False, True), (True, True)],
    ids=["page-extra", "movie-extra", "both-extra"],
)
async def test_discover_ignores_unknown_upstream_fields(
    movies_client,
    movie_api,
    tmdb_search_payload,
    tmdb_search_expected_json,
    add_page_field,
    add_movie_field,
):
    endpoint = "/movies/discover"
    parameters = {"page": 2}
    base_payload = deepcopy(tmdb_search_payload)
    extended_payload = deepcopy(base_payload)
    extra_field_name = "provider_debug"
    extra_field_value = {"marker": "provider-only-test-marker"}
    expected_json = deepcopy(tmdb_search_expected_json)
    expected_status = 200
    expected_upstream_count = 2
    expected_database_calls = []
```

## Задание

1. Если `add_page_field` равен True, добавь `extra_field_name` со значением `extra_field_value` в `extended_payload`. Если `add_movie_field` равен True, добавь такое же поле в `extended_payload["results"][0]`.
2. Проверь, что добавленное поле отсутствует в исходной странице и исходном первом фильме `base_payload`. Исходная фикстура `tmdb_search_payload` также должна остаться без этого поля. Проверка отсутствия ключа: `assert key not in dictionary`.
3. Настрой `movie_api.use_upstream` на ответ 200 с `base_payload`. Выполни запрос `movies_client.get(endpoint, params=parameters)` с await. Проверь статус и точный JSON по `expected_json`.
4. Перенастрой обработчик на `extended_payload` и повтори тот же запрос. Проверь 200 и равенство JSON первому ответу. Проверь отсутствие строки-маркера в теле второго ответа.
5. Проверь ровно два внешних запроса и отсутствие обращений к БД. Функции `get_by_id`, `get_by_tmdb_id`, `list_movies`, `save` у `movie_api` должны остаться невызванными.

Значения флагов передаются через parametrization. Дополнительный цикл по вариантам внутри функции не нужен. Для первых двух запросов используй отдельные переменные Response, а `.json()` вызывай после проверки статуса.

## Границы
