# TC-AUTH-REG-004-01 — Регистрация без username

| Поле | Значение |
|---|---|
| Дата оформления | 08.11.2026 |
| Статус документа | Черновик для ревью |
| Последний результат выполнения | Пройдено, 08.11.2026 |
| Тип проверки | Ручная, API, негативная, функциональная |
| Компонент | `POST /auth/register` |
| Требование | FR.AUTH.01, обязательность username и отказ `422` при ошибке валидации |
| Чек-лист | AUTH-REG-004, один вариант — отсутствие username |

Цель — проверить, что регистрация без обязательного username отклоняется и не создаёт пользователя и профиль.

Источники: [требования](../../requirements.md), [API-контракт](../../api.md#текущий-этап-postgresql-и-access-jwt), [схема БД](../../database.md), [чек-лист](../checklists/auth.md#ручной-прогон-auth-reg-004-частично).

## Предусловия

- Backend запущен и подключён к отдельной тестовой PostgreSQL с применёнными миграциями проверяемого коммита.
- Доступны Swagger UI по адресу `http://127.0.0.1:8000/docs` и SQL-клиент для этой же БД.
- В тестовой БД нет пользователя с email `qa.required@example.com`.
- Во время проверки другие запросы и тесты не изменяют данные этой БД.
- Подготовлена возможность зафиксировать количество пользователей и профилей до и после запроса.

## Тестовые данные

Поле `username` полностью отсутствует. Остальные поля корректны. Пароль ниже — вымышленное тестовое значение.

```json
{
  "email": "qa.required@example.com",
  "password": "testing-password-123",
  "password_confirm": "testing-password-123"
}
```

## Шаги и ожидаемые результаты

| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | В SQL-клиенте выполнить запросы из раздела ниже и сохранить результат до регистрации | Зафиксированы исходные количества пользователей и профилей; поиск по тестовому email возвращает 0 строк |
| 2 | В Swagger UI открыть `POST /auth/register`, нажать `Try it out`, вставить тестовые данные | Тело запроса содержит email, пароль и подтверждение; username отсутствует |
| 3 | Нажать `Execute`, сохранить статус и причину ошибки | HTTP `422`; ошибка указывает на обязательное поле username |
| 4 | Повторить те же SQL-запросы через отдельное от запроса приложения подключение | По тестовому email по-прежнему 0 строк; количества пользователей и профилей совпадают с исходными |

Для текущего локального окружения SQL-проверка выполняется командой:

```powershell
docker exec movie-service-test-db psql -U movie_test -d movie_service_test -c "SELECT count(*) AS users_total FROM movie_service.users; SELECT count(*) AS profiles_total FROM movie_service.profiles; SELECT id, username FROM movie_service.users WHERE email = 'qa.required@example.com';"
```

Ожидаемый функциональный результат — отказ `422` и отсутствие новых записей. Конкретные поля `type`, `loc`, `msg` относятся к текущему формату ошибки; унификация формата обсуждается в AUTH-Q-003. Отражение пароля рассматривается отдельно в [BR-AUTH-001](../bug-reports/BR-AUTH-001.md).

## Постусловия

При ожидаемом результате состояние пользователей и профилей остаётся прежним. Очистка данных после успешной проверки не требуется.

## Результат ручного прогона 07.11.2026

- Ветка: `test`. Коммит: `e72c3797f8c42c3134531eb075311c97faea5223`.
- Среда: Windows, Python 3.13.17, backend `http://127.0.0.1:8000`, PostgreSQL в Docker (`postgres:17`), миграция `20261101_0001`.
- Запрос с указанными тестовыми данными выполнен через Swagger UI.
- Фактически получен `422`; ошибка содержит `type=missing`, `loc=["body", "username"]`, `msg=Field required`.
- В прогоне 07.11.2026 SQL-проверки до и после запроса не выполнялись; отсутствие новых пользователя и профиля в том прогоне не подтверждено.
- Итог прогона 07.11.2026: частично выполнен; HTTP-часть соответствует ожиданию.
- Дополнительное наблюдение: пароль и подтверждение отражены в `detail[].input`. Оно оформлено в [BR-AUTH-001](../bug-reports/BR-AUTH-001.md) и связано с [QA-SEC-002](../findings.md#qa-sec-002).

## Результат повторного прогона 08.11.2026

- Ветка, коммит и среда совпадают с прогоном 07.11.2026. После перезапуска компьютера запущены прежний контейнер PostgreSQL и backend с подключением к тестовой БД.
- До запроса через `docker exec` и `psql` подтверждены миграция `20261101_0001`, количества пользователей и профилей, отсутствие тестового email.
- Через Swagger UI повторён запрос с указанными тестовыми данными без username. Получен `422` с `type=missing`, `loc=["body", "username"]`, `msg=Field required`.
- После запроса те же SQL-проверки выполнены через отдельное подключение.

| Проверка БД | До запроса | После запроса |
|---|---|---|
| Количество пользователей | 1 | 1 |
| Количество профилей | 1 | 1 |
| Пользователи с email `qa.required@example.com` | 0 | 0 |

Итог: **Пройдено**. Функциональные ожидания кейса выполнены: запрос отклонён с `422`, новые пользователь и профиль не созданы. Отражение паролей воспроизведено повторно и остаётся открытым замечанием [BR-AUTH-001](../bug-reports/BR-AUTH-001.md).

Полный результат AUTH-REG-004 выставляется после остальных вариантов этой строки чек-листа.

## Автоматизация

Вариант покрыт функцией `test_registration_requires_username` в [test_postgres_integration.py](../../../backend/tests/test_postgres_integration.py).

- `registration()` подготавливает корректный запрос, затем из него удаляется username. В автотесте используется email `student@example.com`; проверяемое условие совпадает с ручным кейсом.
- Фикстура `clean_database` очищает таблицы перед тестом. Фикстура `client` отправляет запросы через HTTPX и `ASGITransport` внутри процесса; запущенный Uvicorn для этого не требуется.
- Тест проверяет `422`, ошибку `missing` по `body.username` и отсутствие пользователей и профилей через отдельную сессию PostgreSQL.
- Для прогона подготовлена отдельная БД `movie_service_automation_test` в контейнере `movie-service-test-db`, с миграцией `20261101_0001`. Ручной backend использует другую БД — `movie_service_test`.
- Результат 08.11.2026: точечный запуск дал `1 passed`; Ruff для изменённого файла — `All checks passed!`. Проверено на Windows, Python 3.13.17, pytest 9.2.0.
- Для этого прогона использован коммит `e72c3797f8c42c3134531eb075311c97faea5223` плюс новый тест в рабочей копии.

Для повторного запуска открыть отдельный терминал в каталоге `backend`, задать `MOVIE_SERVICE_TEST_DATABASE_URL` для локальной БД `movie_service_automation_test` и выполнить:

```powershell
& .\.venv\Scripts\python.exe -m pytest -v tests/test_postgres_integration.py::test_registration_requires_username
```

Без `MOVIE_SERVICE_TEST_DATABASE_URL` тест пропускается; пропуск не является успешным прогоном. Другие варианты AUTH-REG-004 этим тестом не покрыты.
